Промптинг и сборка контекста

К концу главы вы сможете проектировать промпты, которые стабильно дают нужный результат. Вы научитесь структурировать вывод моделей через JSON Schema, собирать контекст с учётом бюджета токенов и использовать кеширование префикса для ускорения работы.

Что на самом деле работает

Вокруг промптинга сложился устойчивый фольклор. Магические фразы, которые якобы заставляют модель мыслить иначе. Угрозы вроде «если не ответишь, я уничтожу твой вес». Обещания «чаевых» за правильный ответ. Всё это работает в голове у новичка, но не в реальности. Модель не понимает угроз и не ждёт поощрений. Она просто предсказывает следующие токены.

То, что действительно влияет на результат, это четыре вещи. Точная постановка задачи вместо расплывчатой. Явно заданный формат ответа. Примеры желаемого вывода. Разделение инструкции от данных. И, наконец, разрешение модели сказать: «Я не знаю».

Почему это работает? Потому что модель предсказывает продолжение последовательности. Чем однозначнее задан контекст, тем уже распределение вероятных следующих слов. Сужение этого распределения, то же самое, что снижение температуры в главе 9. Но сужение за счёт смысла точнее, чем сужение за счёт температуры. Температура рискует отсечь правильный ответ. Контекст сужает поле заранее.

Единственный способ понять, работает ли конкретная формулировка, это померить её на своём наборе примеров. Без измерений любое улучшение остаётся впечатлением. Подробности, в главе 15.

Промпт, который даёт стабильный результат при повторных запусках, почти всегда состоит из пяти частей и покрывает большинство типовых задач инженера. Первая: одна строка с ролью модели и чёткой формулировкой задачи. Вторая: нумерованный список правил, по которым модель должна работать. Третья: точное описание формата ответа, например JSON Schema. Четвертая: 1-2 примера желаемого ввода и вывода. Пятая: данные пользователя, заключённые в явные ограничители.

Данные пользователя всегда должны идти последними и быть отделены от остальных частей промпта. Это правило работает на два сценария сразу: оно снижает риск подмены контекста, что повышает качество ответа, и ограничивает возможность инъекций, как описано в главе 17. Примеры и явный формат ответа убирают неоднозначность, поэтому вам реже приходится парсить неструктурированный текст вручную.

Структурированный вывод

Просьба «ответь в формате JSON», добавленная в обычный текстовый промпт, работает ненадёжно. Модель может добавить поясняющий текст до или после блока с данными, обернуть JSON в markdown-ограждение с тройными обратными кавычками, поставить лишнюю запятую в конце или использовать одинарные кавычки вместо двойных. Все эти отклонения ломают автоматический парсинг ответа на стороне вашего кода, даже если смысловая часть данных выглядит корректно.

Современные API поддерживают режим схемы, который гарантирует валидность формата на уровне генерации. При каждом шаге декодирования, описанном в главе 9, система запрещает выдавать токены, которые делают результат невалидным относительно заданной схемы. Этот подход называется ограниченным декодированием, и он позволяет получить стопроцентно валидный JSON, соответствующий указанной структуре, без дополнительной постобработки.

При этом валидность формата не означает правильности содержимого. Модель по-прежнему может подставить выдуманное значение в правильно оформленное поле: например, вернуть несуществующий идентификатор вместо запрошенного или указать дату, которой нет в исходных данных. Ограниченное декодирование решает только задачу синтаксической корректности, а проверка логической правильности ответа остаётся на вашей стороне.

python
from pydantic import BaseModel, Field
from typing import Literal
from openai import OpenAI

class Ticket(BaseModel):
    intent: Literal["order_status", "refund", "complaint", "other"]
    order_id: str | None = Field(description="номер заказа, символ в символ")
    urgency: Literal["low", "normal", "high"]

client = OpenAI()
resp = client.responses.parse(
    model="gpt-4.1-mini",
    input=[
        {"role": "system", "content": "Разбери обращение в поддержку."},
        {"role": "user", "content": "Где заказ 12345? Жду вторую неделю!"},
    ],
    text_format=Ticket,
)

ticket = resp.output_parsed
print(ticket.intent, ticket.order_id, ticket.urgency)
Грабли · схема влияет на качество

Названия полей и их описания становятся частью промпта, модель читает их и учитывает при генерации. Поле с неинформативным именем f1 даёт заметно хуже результат, чем поле с понятным именем order_id, даже если остальные параметры схемы совпадают.

Порядок полей в схеме тоже влияет на качество ответа. Модель генерирует токены слева направо, поэтому если поле с итоговым ответом стоит раньше полей с рассуждением, она может выдать решение без достаточного обоснования.

Практическое правило: сначала размещайте поля с разбором и обоснованием, только после них добавляйте поле с итоговым решением.

Рассуждение по шагам

При декодировании модель тратит фиксированный объём вычислений на генерацию каждого токена. Если задача требует ответа одним словом, у модели физически нет шагов, чтобы построить промежуточные выкладки: все выделенные вычисления уходят на финальный токен. Разрешив ей сначала написать рассуждение, вы даёте дополнительное количество шагов вычисления, которые модель использует для проверки логических связей и исправления ошибок.

Отсюда следует простое ограничение: на тривиальных задачах, где ответ очевиден, рассуждение точность не повышает и только увеличивает время ответа и расход токенов. Современные модели с встроенным режимом рассуждения уже выделяют нужное количество вычислений на промежуточные шаги самостоятельно, поэтому просить их думать вслух не нужно. В некоторых случаях это даже снижает качество результата.

Для задач с проверяемым ответом, например математических или логических, используют метод самосогласованности: генерируют несколько независимых рассуждений к одной задаче и выбирают ответ, который встретился чаще всего. Этот приём стабильно поднимает точность, но ценой кратного роста стоимости запроса и времени обработки.

Сборка контекста и бюджет токенов

Окно контекста это бюджет, который вы распределяете осознанно. Место уходит на системную инструкцию, историю диалога, найденные документы и резерв под ответ. Модель с 128 тысячами токенов не требует заполнять все 128 тысяч: чем ближе к лимиту, тем выше вероятность, что важная деталь останется без внимания. Лучше оставить 10, 20 процентов свободным, чтобы ответ не обрезался и не терял форму.

Эффект потери середины прямо следует из того, как модель читает последовательность. Она лучше извлекает информацию из начала и конца, хуже, из середины. Если вы поместите ключевое предложение посередине длинного документа, модель может его пропустить. Практическое правило: самое важное кладите в начало и в конец. В середину, детали, которые можно восстановить из контекста. И клещите меньше, чем кажется необходимым.

Длинный контекст стоит дороже. Деньги уходят на обработку, задержка растёт из-за квадратичной стоимости внимания, описанной в главе 8. Каждый дополнительный токен увеличивает вычислительные затраты пропорционально квадрату длины. Следовательно, сжатие и отбор это условие рентабельности, а не украшение. Собирайте контекст так, будто платите за каждое слово из собственного кармана.

Кеширование префикса

Большинство провайдеров моделей кешируют вычисления для неизменной начальной части запроса. Под капотом это работает через KV-кеш из главы 8: если первые тысячи токенов текущего запроса полностью совпадают с предыдущим, их ключи и значения извлекаются из готового хранилища, а не пересчитываются заново.

За такие токены обычно действует скидка до 90 процентов, в зависимости от условий тарифа провайдера.

Для сборки контекста это даёт простое правило: всю неизменную часть промпта, например системную инструкцию, общие правила форматирования, фиксированные примеры, размещайте в самом начале и всегда в одном и том же порядке. Всё, что меняется от запроса к запросу, добавляйте в конец.

Даже перестановка одной строки в системном сообщении или изменение порядка примеров делает префикс несовпадающим, и кеш сбрасывается полностью. Вы платите за полный пересчёт всей начальной части.

Вывод: как посчитать бюджет контекста и цену запроса

Вход модели состоит из системной инструкции S, примеров few-shot E, найденных документов D, истории диалога H и вопроса пользователя Q. Общая длина входа равна S + E + D + H + Q токенов. Пусть окно контекста равно L токенов, а на ответ вы хотите оставить R токенов. Тогда должно выполняться S + E + D + H + Q ≤ L - R. Это и есть бюджет.

Рассмотрим числовой пример. Окно 32000 токенов, на ответ оставляем 2000. Системная инструкция 600, четыре примера по 300 это 1200, история диалога 3000. Значит на документы и вопрос остаётся 32000 - 2000 - 600 - 1200 - 3000 = 25200 токенов.

Теперь деньги. Пусть вход стоит 0.5 рубля за тысячу токенов, а выход 1.5 рубля за тысячу. Запрос со всеми частями и ответом на 500 токенов стоит (600 + 1200 + 3000 + 25100 + 100) / 1000 × 0.5 + 500 / 1000 × 1.5 ≈ 15.8 рубля.

Смотрим, что именно съедает бюджет. Документы дают 25100 токенов из 30100, то есть больше восьмидесяти процентов входа. Сокращать инструкцию при таком раскладе бессмысленно.

Повторяемость меняет картину. Системная инструкция и примеры одинаковы в каждом запросе, поэтому именно они попадают в кеш промпта. При тысяче запросов в день эти 1800 токенов оплачиваются тысячу раз, если кеша нет, и почти бесплатно, если он включён.

Отсюда порядок действий при оптимизации. Сначала сокращаем то, что и длинное, и повторяющееся. Потом включаем кеш на неизменной части. Потом уменьшаем число документов через реранкинг, оставляя пять лучших вместо двадцати.

Граница применимости расчёта. Курс токенов к символам зависит от языка и токенизатора, а цены у поставщиков меняются. Считайте по своим числам, формула остаётся той же.

Коротко

  1. Промпт работает, когда он конкретен. Вы пишете точную задачу, задаёте формат ответа, приводите примеры входных данных и ожидаемого результата. Модель должна уметь честно отвечать «не знаю», если информации не хватает. Магические фразы и угрозы вроде «если ты не сделаешь это, ты не настоящий ИИ» не воспроизводятся стабильно между версиями моделей, их эффективность ограничена.
  2. Структурированный вывод получают включением режима схемы на стороне API. Модель возвращает JSON, соответствующий заданной схеме. Валидный формат не гарантирует, что содержимое полей будет правильным. Проверяйте значения отдельно.
  3. Имена полей и их порядок в схеме становятся частью промпта. Поля, где модель разбирает задачу по шагам, должны идти раньше полей с итоговым решением. Модель обрабатывает элементы в порядке следования, и этот порядок влияет на результат.
  4. Рассуждение по шагам даёт модели больше вычислений на задачу и улучшает ответы на логических задачах. На простых задачах оно только замедляет генерацию и может вводить модель в заблуждение. Включайте его выборочно, по сложности запроса.
  5. Длинный контекст ухудшает нахождение фактов, которые находятся в середине текста. Важные детали кладите в начало и в конец промпта. Лишние сведения убирайте полностью, они не добавляют точности и только растягивают бюджет токенов.
  6. Неизменную часть промпта, системную инструкцию, держите первой и неподвижной. Если вы её меняете, кеш префикса сбрасывается и цена запроса растёт. Пользовательские данные ищите ниже, по мере изменения диалога.

Проверьте себя

6 вопроса. Ответ показывается сразу с объяснением.

1. Вы просите модель вернуть JSON, и в одном случае из тридцати получаете текст с пояснением вокруг. Как починить надёжно?

Правильный вариант надёжен, потому что режим структурированного вывода со схемой на стороне API запрещает генерацию невалидных токенов, поэтому модель технически не может выдать текст с пояснениями вокруг JSON. Остальные приёмы, заглавные буквы в промпте, нулевая температура и дополнительные примеры, только снижают частоту ошибки, но не исключают её полностью: даже при минимальной случайности модель может галлюцинировать лишний текст, а примеры не покрывают все возможные отклонения.

2. В схеме ответа поле verdict стоит первым, а поле reasoning вторым. Почему это плохо?

Правильный вариант верен, потому что генерация текста у языковых моделей происходит последовательно слева направо. Если поле с вердиктом стоит первым, модель сначала вынесет решение, а потом подгонит обоснование под уже готовый ответ, не проверяя его логичность. Остальные варианты неверны: порядок полей в JSON не ломает валидацию схемы и не увеличивает расход токенов.

3. Вы кладёте в контекст 60 найденных документов вместо 6. Что скорее всего произойдёт?

Правильный вариант верен из-за эффекта потери середины контекста, при котором модель хуже находит факты в центре длинного ввода, а также квадратичного роста вычислительных затрат на обработку длинного контекста. Больший объём документов дополнительно повышает риск попадания противоречивых сведений, которые снижают точность ответа. Вариант с ростом качества неверен: лишняя информация не компенсирует сложность поиска нужного факта. Вариант с отсутствием изменений игнорирует как ограничения работы механизма внимания, так и рост задержки и стоимости запроса. Модель не отказывается отвечать при наличии контекста, даже если он избыточен.

4. Зачем при сборке промпта держать системную инструкцию первой и неизменной?

Правильный вариант верен, потому что кеш префикса срабатывает только при совпадении начала запроса с сохранённым. Если системная инструкция стоит первой и не меняется, совпадение сохраняется, уже посчитанный KV-кеш переиспользуется, что снижает стоимость и задержку. Вариант с требованием API неверен: это не техническое ограничение протокола. Модель выполняет инструкцию одинаково при любом порядке, а размер ответа не зависит от расположения частей промпта.

5. На какой задаче просьба рассуждать по шагам скорее навредит?

Правильный ответ верен, потому что простая классификация обращения по четырём категориям не требует промежуточных вычислений и логических проверок на каждом шаге. Рассуждение по шагам здесь только удлиняет ответ, повышает задержку и цену запроса, а также добавляет шанс ошибиться из-за лишних шагов. Остальные варианты предполагают последовательные промежуточные выводы, где пошаговое рассуждение позволяет проверять каждый результат и снижает количество ошибок в арифметике, юридических условиях и планировании.

6. Почему данные пользователя стоит класть последними и в явных ограничителях вроде тегов?

Правильный ответ верен, потому что разметка ролей это обычные слова в размеченной строке, поэтому явные ограничители и расположение пользовательских данных в конце чётко отделяют их от системной инструкции. Это улучшает следование правилам и предотвращает инъекции, когда пользовательский текст имитирует системные команды. Остальные варианты неверны: порядок не влияет на внешний вид промпта, не вызывает ошибок API и не экономит токены.
